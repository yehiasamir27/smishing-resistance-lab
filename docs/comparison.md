# Second-factor comparison: which relay step does each factor break?

The lab's phishing relay succeeds by forwarding whatever the victim enters to
the real service in real time. A second factor is only *phishing-resistant* if
it breaks one of the relay's steps in a way the attacker cannot work around.

| Factor | SIM-swap / SS7 risk | Relayable by a live MITM? | What breaks (or doesn't) | Verdict |
|--------|:---:|:---:|--------|--------|
| **SMS OTP** | ❌ High | ❌ **Yes** | Code isn't bound to who's logging in; attacker forwards it. Demonstrated in `attack/`. | Weakest |
| **TOTP app** (Google Authenticator, etc.) | ✅ None | ❌ **Yes** | Removes SIM-swap/SS7, but the code is still a shared secret the victim types → relayable, same as SMS. | Better, not resistant |
| **Push / number-matching** | ✅ None | ⚠️ Partially | User *may* notice location/device mismatch in the prompt — but it relies on a human catching it. | Depends on the human |
| **Passkey / FIDO2 / WebAuthn** | ✅ None | ✅ **No** | Signature is bound to the page's **origin**. Attacker can't present the true origin (rejected) nor forge it (breaks the signature). Demonstrated in `defense/`. | Phishing-resistant |

## Why only passkeys close the relay

Everything above the last row shares one weakness: **the secret is portable.**
A code — whether it arrives by SMS or is generated by a TOTP app — is just a
string the victim types, and a string can be forwarded.

A passkey is different in kind. The authenticator signs a challenge together
with the **origin of the page the browser is actually on**, and the browser
stamps that origin itself — page JavaScript cannot change it. So:

- On the phishing page, the signature covers the attacker's origin → the real
  service rejects it (origin mismatch).
- If the attacker edits the origin to look right, the signature no longer
  matches the data → rejected (invalid signature).

The binding is cryptographic and enforced by the browser, not by user
vigilance. That is the whole reason the industry (FIDO Alliance, Apple, Google,
Microsoft) is moving from SMS/TOTP to passkeys.

## Mapping to the lab

- `attack/` — proves the **SMS OTP** row: a working relay ending in takeover.
- `defense/webauthn_demo.py` — proves the **passkey** row with real ECDSA, three
